# Session 004 — Win-Loss & Full Match — Log

**Date:** 2026-09-11
**Branch:** session-004/1
**Roadmap section:** Pass 4 — Win/loss + full match

## What was built

### Phase 1 — Shared plumbing

- `Remotes.luau` — added `RoundResult` and `MatchResult` to `EVENT_NAMES`.
- `Types.luau` — added `Score` (`{ [number]: number }`, UserId -> rounds won), `RoundResult`
  (`{ winner: Role, reason: "survived" | "direct" | "crushed" }`), `MatchResult`
  (`{ winner: number?, score: Score }`), and a `score` field on `StatePayload`.
- `Config.luau` — added `ResolveSettleTime = 1.5`.

### Phase 2 — `PrincessMonitor.luau` (new)

- Tracks dead/armed state; `arm()`/`disarm()`/`isDead()`/`reason()`.
- Direct-hit path: `reportDirectHit()`, called from `WeaponManager.onHit` when a projectile's
  raycast lands on the part named `Princess` (the raycast filter already included her since
  session 003's boundary fix — this session only had to extend what happens on that hit).
- Moving-block path: `Touched` on the Princess part, checking any `BlockId`-tagged part's
  `AssemblyLinearVelocity.Magnitude > Config.MovingBlockKillSpeed` — no owner check, so the
  Builder's own wall counts, per spec.
- Notifies `MatchController` via a registered callback (`onDeath`) the instant a kill happens,
  rather than being polled between shots — a kill during the post-shot physics settle window
  needs to end the round immediately, not wait for the next `FireWeapon`.

### Phase 3 — Arena reset split

- `Arena.build()` stays the one-time static-geometry builder (ground, boundary, markers,
  piles, Princess), called once at server start.
- New `Arena.resetRound()` — the lighter per-round path: repositions the Princess only (she's
  anchored, so no velocity to clear). Leaves the static geometry and the Blocks folder
  untouched.

### Phase 4 — Round loop (`MatchController.luau`)

- Full BUILD -> ATTACK -> RESOLVE -> SWAP loop for `Config.RoundsPerMatch` (4) rounds.
- ATTACK ends (via `consumeShot()` hitting zero, or a `PrincessMonitor` death callback)
  transition into RESOLVE, which waits `Config.ResolveSettleTime` before reading the outcome
  -- keeps `PrincessMonitor` armed through the settle window so a late block-topple from the
  last shot can still register as a kill.
- SWAP flips `roles.builder`/`roles.attacker`, increments `round`, and runs a shared
  `startRound()` (Princess reposition, round-reset hooks, block respawn, fresh block budget,
  back to BUILD, reposition both characters).
- Score tracked per `UserId` (survives the role flip, unlike a builder/attacker-keyed score
  would). Match winner = higher score; equal scores broadcast `winner = nil` (tie).
- Added `MatchController.onRoundReset(callback)` — a registration hook so other services can
  clean up their own live state each round without `MatchController` requiring them back
  (which would have created a require cycle, since those services already require
  `MatchController`). `WeaponManager` registers `clearAll()` (despawns in-flight projectiles)
  through this.
- `init.server.luau` — `BlockManager.spawnAll()`'s standalone call was removed; it's now
  handled inside `MatchController.start()`'s initial `startRound()` call, alongside
  `PrincessMonitor.start()` being wired in.

### Bug found and fixed outside the brief's file list

- `BuildManager`'s `occupancy` table (cell -> blockId) was never reset between rounds. Since
  `BlockManager.spawnAll()` resets its own id counter to 1 each round, round 2's BUILD phase
  would have inherited round 1's stale occupancy entries and misjudged placements. Fixed with
  a `BuildManager.resetOccupancy()` registered through the same `onRoundReset` hook used by
  `WeaponManager`. `BuildManager.luau` wasn't in the brief's modify list — this only surfaced
  because it was the first session to actually run a second BUILD phase.

### Phase 5 — HUD / client

- `Hud.luau` — added round number ("Round X of 4") and running score ("Score — You: N
  Opponent: M"), visible whenever both roles are known.
- `ResultBanner.luau` (new) — centered banner for `RoundResult` (fades after 3s) and
  `MatchResult` (stays up). Tracks `StateChanged` only to know the local player's role at the
  moment a `RoundResult` arrives, since roles flip on SWAP right after.
- `init.client.luau` — wired `ResultBanner.start()`/`.update()` alongside the other client
  modules.

## Playtest result

User played the full loop through several two-player Studio playtests: BUILD -> ATTACK -> a
kill or a survive -> RESOLVE -> SWAP, repeated through all 4 rounds to a match result. Reported
working correctly — round resolution, role swap, and the best-of-4 match all functioned as
specced. No bugs reported from this session's own scope. Assessment was on game feel, not
correctness: "it is working and it is not fun at all yet" — the BUILD phase with uniform
rectangular blocks reads as rote, with no interesting variation in how a wall can be built.
That feedback became the seed for session 005 (see below), not a defect in this session's
work.

  decided, to let physics settle).

## Notes for next session

Session 004's own scope (win/loss + full match) is complete and playtested green — the spec's
full Definition of Done runs start to finish. The user's post-playtest feedback was about feel,
not correctness: the uniform rectangular block roster makes BUILD rote. Rather than fold a fix
into this already-closed session, a new Pass 5 was inserted ahead of the old "Tune, then
launch" pass (now Pass 6): replace the 6 Standard + 6 Wide roster with 12 identical L-shaped
four-cell pieces, generalizing the grid/placement pipeline from a rectangular footprint +
2-state flip to an arbitrary multi-cell shape + full 4-state rotation. `roadmap.md` §6 already
reflects this insertion. Session 005's brief is drafted at
`sessions/005. Irregular Blocks — L-Piece Pilot — Brief.md`; its Starting State section carries
forward five decisions already settled in conversation (physics-only stability challenge, a
`UnionOperation` per L-piece, 4x-Standard mass, a full roster swap rather than an addition, and
4-state rotation) so they don't need to be re-litigated at that session's Open Gate — only the
exact L-piece cell geometry, union attribute behavior, and ghost fidelity are still open.
Separately: `src/client/BuildInput.luau` has not been touched or re-read since session 001 --
session 005 will be the first session since then to open it, so read it fresh rather than
trusting the roadmap's summary of it.
