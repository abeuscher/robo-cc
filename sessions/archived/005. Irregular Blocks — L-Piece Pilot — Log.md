# Session 005 — Irregular Blocks — L-Piece Pilot — Log

**Date:** 2026-09-11
**Branch:** session-005/1
**Roadmap section:** Pass 5 — Irregular Blocks (L-Piece Pilot)

## What was built

### Phase 1 — Shared shape model

- `Config.luau` — collapsed the 6 Standard + 6 Wide roster into one `LPiece` type: a `Shape`
  field (4 local cell offsets forming a standard L-tetromino — three in a row along the top,
  one hanging below the row's left end), `Count = 12`. `Rotatable` dropped entirely — every
  shape now gets full 4-state rotation, no per-type gate.
- `Types.luau` — `PlacePayload.rotated: boolean` → `rotation: number` (0-3); `BlockType` and
  `BlocksRemaining` updated to the single-type roster.
- `GridUtil.luau` — added `rotateShape` (rotates a shape's offsets by quarter-turns and
  re-normalizes to a bottom-left-origin bounding box), `shapeSpan`, `rotatedSpan`. `coveredCells`
  now takes `(shape, anchor, rotation)` instead of a rectangular span; `spanForSize` removed.
  `isInside`/`cellToWorld`/`footprintCentre` untouched, as planned — they already operated
  per-cell, not per-footprint.

### Phase 2 — `BlockManager` — `UnionOperation` blocks

- Each L-piece is built from 4 sub-cubes unioned via `part:UnionAsync()` into one
  `UnionOperation`, rather than a single plain `Part`. Same density-based
  `CustomPhysicalProperties` formula applied to the union — mass comes out to 4× a sub-cube's
  mass automatically, since density × total volume falls out of the existing formula with no
  separate mass constant needed.
- Roblox doesn't document where a fresh `UnionOperation`'s `.CFrame` sits relative to its own
  geometry after `UnionAsync()`, so each block instance's actual pivot offset (`pivotDelta`) is
  measured once right after it's built (constituent sub-cubes are built in "shape space" —
  bounding-box centre at the world origin, identity rotation — so the union's raw `.CFrame` at
  that moment *is* the offset) and composed into every later `moveToWall`/`returnToPile` call.
  This is what makes rotation pivot correctly around the shape's actual footprint centre
  regardless of whatever internal convention the CSG operation uses.

### Phase 3 — `BuildManager` — shape-based placement

- `onPlaceBlock` walks `GridUtil.coveredCells(typeDef.Shape, anchor, rotation)` instead of a
  rectangular span; `rotation` is clamped to 0-3 (`math.floor(...) % 4`), defaulting to 0 on a
  missing/invalid value rather than rejecting the placement outright, matching the existing
  defensive-but-permissive validation style.

### Phase 4 — Client

- `BuildInput.luau` — the ghost is now a pool of translucent per-cell cubes matching the real
  footprint (grown lazily as needed), not a bounding-box rectangle; `R` cycles all 4 rotations.
  Removed as dead code: the pile-click's `size`/`rotatable`/`rotated` fields on `held`, and
  `placementCFrame` (only ever used by the old single-part ghost).
- `Hud.luau` — the blocks-remaining line changed from `"Standard: %d Wide: %d"` to a single
  count. Not in the brief's file list, but the old format string would have silently frozen at
  `0`/`0` forever once the roster became one type — a real bug, not a style choice.

### Follow-up — cube-shaped sub-blocks

After the initial playtest, the user pointed out the block was shorter than it was wide (1.25
tall × 2.5 wide/deep, per the original spec-locked brick ratio) and asked to switch to cubes.
Settled on shrinking the wider dimensions down to match the height (the smaller of the two)
rather than growing height to match the width. `Config.BLOCK_SIZE` → `Vector3.new(1.25, 1.25,
1.25)`; `GridSize` changed from a separately hardcoded `Vector2.new(2.5, 1.25)` to
`Vector2.new(BLOCK_SIZE.X, BLOCK_SIZE.Y)`, so grid pitch can no longer drift out of sync with
the actual block size. No other file needed touching — confirmed via a full-repo grep for the
old `2.5`/`1.25` literals — because the shape/grid pipeline built earlier this session is fully
parametric.

## Playtest result

Two-player Studio playtest, BUILD phase only (session scope). Reported working: 12 L-pieces
spawn into a single pile, all 4 rotations snap and place correctly, occupancy/bounds validation
holds, and gravity at ATTACK start produces a real physical stability test on any unsupported
overhang. The cube-size follow-up was applied and played through in the same session with no
further issues reported.

User's assessment went beyond "it works": the L-piece pilot "succeeds in making the game more
interesting," but the specific thing identified as responsible was not the shape itself — it
was "the gravity turning on after placement." That distinction became the seed for a scoping
conversation (see below) rather than a defect in this session's own work.

## Config changes

- `BlockTypes` — 6 `Standard` (`2.5×1.25×2.5`) + 6 `Wide` (`7.5×1.25×2.5`) → 12 `LPiece`
  (shape-defined footprint, no per-type rectangular `Size`-as-footprint).
- `BlockSize` — `2.5 × 1.25 × 2.5` → `1.25 × 1.25 × 1.25` (cube).
- `GridSize` — was a separately hardcoded `Vector2.new(2.5, 1.25)`; now derived as
  `Vector2.new(BLOCK_SIZE.X, BLOCK_SIZE.Y)`.
- `BuildZoneSize` — not hand-edited; falls out of the unchanged `Count`/`Size` totals formula.
  Moved from 30×15 to roughly 45×30 when the roster switched to L-pieces (a taller/wider
  bounding box per piece than a single Standard block), then back down to roughly 22.5×30 once
  the cube-size follow-up shrank each piece's footprint. Flagged to the user both times as a
  side effect of Config's existing generic sizing formula, not a deliberate retune.

## Notes for next session

Session 005's own scope (L-piece pilot) is complete and playtested green, plus a same-session
follow-up (cube-shaped sub-blocks) the user asked for after seeing it work. The playtest
feedback was specific in a way that reshapes the near-term roadmap: the user identified gravity
at release — not the L-shape itself — as what makes BUILD interesting, and used that to propose
a larger pivot: remove the physical pile entirely, and replace the fixed L-piece with a
per-placement randomly generated shape (3-6 of 9 cells filled at random within a 3×3 area)
where cells that end up mutually adjacent fuse into one rigid body and cells that end up
isolated stay independently physical — so a single placement can resolve into several
separately-falling pieces at ATTACK start instead of exactly one.

This was scoped in conversation, not implemented — it was assessed as more than one session's
work because it breaks an invariant every prior session (including this one) relied on: one
placed piece has always been exactly one rigid body. It's split into two passes, inserted ahead
of the old Pass 6 "Tune, then launch" (now Pass 8 — see `roadmap.md`):

- **Pass 6 — Piece Queue (Sequential Hand-off).** Remove the physical pile; issue one piece at
  a time from a queue, forced placement before the next is issued. Shape stays the fixed
  L-piece and count stays 12 — this pass is purely the interaction-model change, kept separate
  from the shape-generation work so each half can be playtested in isolation. Brief already
  drafted at `sessions/006. Piece Queue — Sequential Hand-off — Brief.md`, with two open
  questions flagged for that session's Open Gate: whether any undo/rearrange survives (spec
  currently says pieces can be picked up and re-placed before confirming — the sequential model
  may override that), and whether Confirm Wall can end BUILD before the queue is exhausted.
- **Pass 7 — Randomized Piece Generation.** The actual random 3×3 generation and the
  connected-component split into independently-physical sub-bodies. Its brief still needs
  drafting — that's session 006's own close-time precondition, not session 005's.

`GridUtil`'s shape/rotation math and `BuildInput`'s per-cell ghost-pool rendering, both built
this session, are generic enough that neither future pass should need to touch them — Pass 7 in
particular should be able to hand `BuildInput` an arbitrary runtime-generated shape and have the
existing ghost/rotate/place pipeline work unchanged.
