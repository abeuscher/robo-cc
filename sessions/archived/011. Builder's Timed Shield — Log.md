# Session 011 — Builder's Timed Shield — Log

**Date:** 2026-09-12
**Branch:** session-011
**Roadmap section:** Pass 11 — Builder's Timed Shield

## What was built

### Phase 1 — `Config` and the network contract

- Added `ShieldSize` (block-scaled panel: 3x a block's width/height, one block deep),
  `ShieldDistance` (`PrincessDistance - ShieldClearance`, `ShieldClearance = 3`, so it sits closer
  to the Princess than the guard — a last line of defense if the guard's already been knocked
  aside) and `ShieldDuration` (`0.5`).
- Added `ActivateShield` to `Remotes.EVENT_NAMES`.
- Added `shieldAvailable: boolean` to `Types.StatePayload`, always present (not optional like
  `currentWeapon`/`currentShape`) — server stays authoritative and broadcasts it on every
  `StateChanged`, the same treatment `blocksRemaining`/`shotsRemaining` get.

### Phase 2 — Server: own the shield

- `MatchController` owns the one-use flag and validation: `state.shieldAvailable` (reset `true`
  in `startRound()`) and `MatchController.useShield(player)`, which checks Builder role + ATTACK
  phase + unused-this-round and flips the flag — the same split `WeaponManager`/`consumeShot()`
  already has for shots.
- New `ShieldManager.luau` owns only the physical object: on a valid `ActivateShield`, spawns a
  plain anchored `Part` in front of the Princess, colored blue (`ForceField` material), and
  destroys it after `Config.ShieldDuration`; registers with `MatchController.onRoundReset` to
  clear any lingering shield at round end (hygiene — `ShieldDuration` is well under
  `ResolveSettleTime`, so this shouldn't normally trigger).
- Unlike the guard piece (session 010), the shield never unanchors and never gets
  `SetNetworkOwner` — it's a static barrier for its whole life, not a physics body.

### Phase 3 — Client: Builder input during ATTACK

- New `ShieldInput.luau`, mirroring `AttackInput`'s activate/deactivate lifecycle: live only
  while phase is ATTACK and the local player is the Builder, `F` fires `ActivateShield`. A local
  `shieldAvailable` check (mirrored from every `StateChanged`, not just the activation edge) only
  avoids firing a request that can't land — the server is still the real authority.
- Wired into `init.client.luau` alongside the other per-phase input modules.

### Phase 4 — HUD

- Added a shield-ready/used readout (blue, matching the shield's own color) visible for the
  Builder during ATTACK, plus a matching hint line ("F to raise your shield — time it against the
  incoming shot").

### Open Gate decisions

- **Mechanism:** physical object, not a scripted invulnerability window — needs no
  `PrincessMonitor` changes, consistent with sessions 009-010's move away from scripted hit rules.
- **Anchored for its whole duration:** confirmed as a deliberate, scoped exception to "everything
  is real physics" — an unanchored shield could get shoved into the Princess by a heavy hit and
  defeat the point.
- **Builder camera:** none added. `BuildCamera` never forces the Builder's camera away from
  `Custom`, and `MatchController.standFor()` already stands the Builder just behind their own wall
  facing the attacker — free-look alone gives them a usable view of the trench. Confirmed at the
  Open Gate rather than assumed.

## Playtest result

Two-player Studio playtest run by the user after syncing. The playtest conversation focused
entirely on the catapult's arc being too high to block with any buildable wall — not on the
shield itself. That fed directly into two mid-session tuning changes (below); user's assessment
after the retune was "Better," then "Okay. Better." after a follow-up round.

Not independently confirmed this session: whether the Builder actually pressed `F` and saw the
shield spawn, whether a well-timed activation visibly blocked a shot, or whether the one-use limit
was exercised twice in the same round to confirm the second press is a no-op. Worth a closer look
next time the shield comes up in a playtest.

## Config changes

- Added: `ShieldSize` (`Vector3.new(11.25, 9.375, 3.75)` — 3x/2.5x `BlockSize` on X/Y, `BlockSize`
  on Z), `ShieldDistance` (`25`, i.e. `PrincessDistance (28) - ShieldClearance (3)`),
  `ShieldDuration` (`0.5`).
- Changed (mid-session playtest feedback, not originally in this pass's scope):
  `CatapultMinAngle` 20 → 15, `CatapultMaxAngle` 70 → 50 (arc height for a fixed target range
  scales with `tan(angle)`; the new range drops the default midpoint from 45° to 32.5°, roughly
  two-thirds the peak height at the same distance). `PieceCount` 8 → 10 (more blocks per round, a
  follow-up request after the angle retune).

## Notes for next session

Session 012 (Scoring & Points) is already scoped and drafted. Its own Open Gate has two design
questions to settle, both flagged by the roadmap as unresolved: what counts as a surviving
"piece" now that one Builder placement can split into several independent physical bodies at
ATTACK start (score by original piece, or by individual body — `BlockManager.placedParts` already
tracks bodies flatly, not grouped by placement, so body-level is the cheaper build); and what
"not toppled off the platform" means mechanically — a spatial check (still within/above the
platform bounds) versus an orientation check (still standing upright, mirroring the Princess's own
tilt check). Tune point values against this session's current numbers (`CatapultMinAngle`/
`MaxAngle` 15-50, `PieceCount` 10), not session 009's.
