# Session 010 — Guard Piece — Log

**Date:** 2026-09-12
**Branch:** session-010
**Roadmap section:** Pass 10 — Guard Piece

## What was built

### Phase 1 — `Config`

- Added `GuardSize` (1.5x a wall block's own footprint on X/Y, same depth on Z) and
  `GuardDistance` (studs behind the build zone, on the same Z axis `PrincessDistance` already
  uses) — derived as `PrincessDistance - GuardClearance` (`GuardClearance = 6`), so the guard
  sits a fixed 6 studs in front of the Princess regardless of future `PrincessDistance` tuning.
- No new friction/restitution/mass tunables: the Open Gate settled on the guard behaving exactly
  like a wall block, so it reuses `Config.BlockFriction`/`BlockRestitution` and the wall's own
  density formula directly in `Arena.luau`, rather than duplicating separate knobs the way the
  Princess has her own.

### Phase 2 — `Arena` — spawn, position, and reset the guard piece

- `Arena.build()` spawns one `Guard` part per round, a plain box (matching the Open Gate decision:
  fastest, no new geometry work) colored slate grey (`SLATE`) to read as distinct from both the
  wall's grey blocks and the Princess's pink, parented directly under `ActiveRound` (not inside
  `Blocks`, so it's untouched by `BuildManager`'s grid/occupancy logic and by the one raycast
  filter — the catapult's force-estimate aim point — that explicitly excludes the `Blocks`
  folder).
- `Arena.resetRound()` re-anchors and repositions the guard back to its fixed spot, mirroring the
  Princess's own re-anchor/reposition in the same function.
- Added `Arena.releaseGuard()`: unanchor then `SetNetworkOwner(nil)`, the same ordering
  `BlockManager.releaseAll()` and `PrincessMonitor.arm()` already use.

### Phase 3 — Make it a real physical obstacle

- `MatchController.beginAttack()` now calls `Arena.releaseGuard()` alongside
  `BlockManager.releaseAll()` and `PrincessMonitor.arm()`, so the guard becomes a real,
  unanchored, server-owned body at the same moment the wall and the Princess do.
- No explicit "destroyed" rule was added, per the Open Gate decision: the guard can be knocked
  down or aside by ordinary collision, exactly like a wall block, with no special-cased removal
  state.

### Phase 4 — Verify emergent behavior

- Confirmed by reading `WeaponManager` and `AttackInput` rather than modifying them: both
  raycast/collide against everything not explicitly excluded (the aim marker and the local
  character only; the catapult's aim-*point* estimate additionally excludes `Blocks`, but the
  real arc trace does not). Since the guard is a plain `Part` outside the `Blocks` folder, it
  participates in both with no code change, as the brief anticipated.

## Playtest result

Two-player Studio playtest run by the user after syncing. User's assessment: "Better" — no
specific issues reported back against the guard's positioning, appearance, or durability. Not
independently confirmed in this session whether the guard was actually knocked down/aside during
the test or whether the exact two-shot-combo scenario (wall down, follow-up shot) was reproduced
directly; worth a closer look if session 011's playtest surfaces anything guard-related.
