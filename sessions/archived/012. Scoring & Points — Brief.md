# Session 012 — Scoring & Points — Brief

**Roadmap section:** Pass 12 — Scoring & Points (`roadmap.md`)
**Branch:** session-012

## Goal

Replace the binary round win/loss with a points comparison: the Builder is scored on how many
wall pieces survive (not knocked off the platform) at round end, and the Attacker is credited for
whether the Princess fell — tuned so a Princess kill is worth roughly a quarter of the maximum
possible wall-piece score, so the Attacker has a genuine reason to grind the wall down for points
rather than only ever hunting the Princess.

5. The `src/` files likely in play — confirm against the actual code during Phase 1:
   - Likely modify: `src/shared/Types.luau` (`RoundResult`'s data shape — currently
     `{ winner: Role, reason }`, needs a points breakdown), `src/shared/Config.luau` (point value(s)
     — per surviving piece, and a Princess-kill value tuned relative to the wall's maximum),
     `src/server/MatchController.luau` (`finishRound()` currently declares a single deterministic
     winner off `PrincessMonitor.isDead()` and tallies one round-win per player in `state.score`;
     this becomes a points comparison, and `state.score`'s meaning shifts from "rounds won" to
     "cumulative points" — `MatchResult`'s payload shape may not need to change even though its
     semantics do), `src/client/ResultBanner.luau` (currently shows only a winner name and a fixed
     reason string; needs the points breakdown), `src/client/Hud.luau` (the running score readout
     is currently "rounds won" — becomes points).
   - Worth checking, not assumed: `src/server/BlockManager.luau` — `placedParts` is a flat list of
     physical bodies (each tagged with its own `BlockId`), not grouped by which Builder placement

     `BlockManager` needs a new query function or a grouping it doesn't currently keep.
     `src/server/Arena.luau` (platform bounds, if "off the platform" needs a spatial check) and
     `src/server/PrincessMonitor.luau` (already exposes `isDead()`/`reason()` — likely reusable
     as-is for the Princess-kill component of scoring).

## Starting state

- Session 011 is implemented: a once-per-round, Builder-activated timed shield (`ShieldManager`,
  `MatchController.useShield`, client `ShieldInput`) during ATTACK. Playtested; no shield-specific
  issues reported back.
- Mid-session tuning from the same playtest, not itself Pass 11 scope: `Config.CatapultMinAngle`/
  `CatapultMaxAngle` moved from 20–70° to 15–50° (flatter arcs so a tall wall can actually block the
  catapult), and `Config.PieceCount` moved from 8 to 10 (more blocks per round). Both affect how
  much wall typically survives to round end, which is directly relevant to this session's scoring
  curve — expect to tune point values against the current numbers, not session 009's.
- `MatchController.finishRound()` today: `winner = PrincessMonitor.isDead() and "Attacker" or
  "Builder"`, one point added to `state.score[winnerUserId]` per round, best-of-`RoundsPerMatch`.
  No partial credit of any kind exists yet.
- `BlockManager.placedParts` holds every body placed this round (survives to `resetQueue()`'s
  `Destroy()` pass); nothing currently reads it once ATTACK begins.
- Rojo pipeline: known-good (`rojo build` after every change, no lint/type tooling installed).

## Plan

### Phase 1 — `Config` and the scoring data shape

Add tunables for the points formula (per-surviving-piece value, Princess-kill value, tuned to the
roadmap's "roughly a quarter of the maximum possible wall-piece score" target). Settle the two open
questions below, then shape `Types.RoundResult` (and anything `MatchResult` needs) to carry the
breakdown, not just a winner.

### Phase 2 — Server: measure and score

Give `BlockManager` (or wherever fits) a way to count what "survived" at round end, per whatever
Phase 1 settled. Rewrite `MatchController.finishRound()`'s scoring around points instead of a
single deterministic winner; decide how a round's points map onto match-level state (`state.score`
keyed by `UserId` already exists — likely keeps its shape, changes its meaning).

### Phase 3 — Client

Update `ResultBanner` to show the points breakdown per round (and the cumulative match score it
already reads from `MatchResult`). Update `Hud`'s existing score readout from "rounds won" to
points.

### Phase 4 — Playtest

Two-player Studio playtest: confirm points are awarded and displayed correctly for a mix of
outcomes (wall mostly intact, wall mostly destroyed, Princess killed early, Princess killed late),
and that the running/match-end score reads sensibly either way.

## Open questions

Settle these at the Open Gate — the roadmap flags both as unresolved:

- **What counts as a surviving "piece."** Since session 008, one Builder placement can split into
  several independent physical bodies (edge-connected components) at ATTACK start, each with its
  own `BlockId`. Score by original piece (e.g. partial credit — a piece with some components downed
  and some standing) or by individual body (simpler against the current data — `BlockManager`
  already tracks bodies flatly, not grouped by placement, so this is also the cheaper option to
  build)?
- **What "survived"/"not toppled off the platform" means, mechanically.** A spatial check (still
  within/above the platform bounds — knocked off the edge into the gap or off the sides doesn't
  count, but a block merely knocked over in place still does), an orientation check (still
  standing upright, mirroring the Princess's own tilt check), or some combination? The roadmap's
  wording ("not toppled off the platform") reads more like the spatial interpretation, but this
  should be confirmed rather than assumed.

## Process rules

- Read every file you intend to modify before editing it.
- All game state and physics is server-authoritative. Clients send intent only; the server
  validates role, phase, and limits on every remote.
- Every tunable lives in `src/shared/Config.luau`. No gameplay magic numbers in logic.
- One ModuleScript per responsibility. `init.*.luau` scripts only bootstrap.
- `src/shared` never requires from `src/server` or `src/client`.
- Match the existing code style. No comments or type annotations on code you did not write.
- Adapt silently to small drift between this brief and the code; note it in one line. Pause
  and ask only for decisions that are expensive to reverse — data shape, new abstractions,
  changes to the arena or physics model.
- A question from the user is a question, not an instruction to act.
- When implementation is done: sync in Studio, run a two-player playtest, report what you
  saw. Then stop — do not start the close until the user says so.
