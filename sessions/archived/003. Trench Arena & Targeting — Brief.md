## Goal

Rework the ATTACK-phase arena into a trench sized off the block totals, give the Attacker two
fixed weapon emplacements chosen between at the start of their turn instead of a mid-turn `F`
toggle, and replace the single locked camera from session 002 with three selectable views
(top-down default, first-person, 45°-down side) so aiming reads clearly regardless of which
weapon or shot is up.

## Starting state

- ATTACK phase (session 002) is complete and playtested: wall release, both weapons fire
  through an identical two-click launch meter (linear fill, one up-and-down pass, target tick,
  green-on-wall-hit crosshair, dashed path preview), shots deplete and the phase holds at 0.
- **Weapon selection today:** `F` freely toggles Ballista/Catapult at any point during the
  Attacker's turn, including between individual shots. `WeaponView` builds one crude prop per
  weapon at a single shared firing spot (`BASE` in `WeaponView.luau`) and swaps visibility on
  toggle. This session replaces that with two separate fixed emplacements and a turn-start
  choice — **open question below on whether the choice locks for the whole turn or repeats
  per shot.**
- **Camera today:** `AttackCamera.luau` locks `CameraMode = Classic` with
  `CameraMinZoomDistance`/`CameraMaxZoomDistance` both set to 8 studs (a fixed close
  over-the-shoulder view) for the Attacker during ATTACK — landed there after two rounds of
  iteration (a scripted side-on `Scriptable` CFrame view, then true `LockFirstPerson`, then
  this). None of that code is a mode system; it's a single fixed view with no toggle. The
  `LockFirstPerson` and zoom-lock techniques both work and are the building blocks for the
  three-mode system this session adds — the discarded scripted side-view CFrame math is not
  preserved in the current file, so a 45°-down view needs re-deriving, not recovering.
- **Aiming today:** `AttackInput.luau` fixes `MUZZLE_ORIGIN` at
  `Vector3.new(0, GroundLevel + MuzzleHeight, -(GapWidth/2))`. Ballista aim is a single
  continuous raycast (fixed in session 002 to stop "grid-snapping"). Catapult aim ignores the
  wall on purpose (also fixed in session 002, so standing close to a tall wall doesn't block
  the player's own aim ray) but is still blocked by everything else (ground, platforms,
  Princess). Both of these fixes must survive the trench resize and the move to two muzzle
  positions — the trench changes distances and sightlines; verify targeting still isn't
  "grid-hoppy" or wall-blocked in the new geometry, don't just assume the fix transfers.
- **Config today (relevant constants):** `GapWidth = 40`, `PlatformSize = Vector3(56, 1, 30)`,
  `BuildZoneSize = Vector2(20, 10)`, `GridSize = Vector2(2.5, 1.25)`, `PrincessDistance = 14`,
  `MuzzleHeight = 0.75`, `BlockTypes` = 6 Standard (`2.5×1.25×2.5`) + 6 Wide
  (`7.5×1.25×2.5`, rotatable) = 12 blocks total, each 1.25 studs tall. These feed the trench
  sizing formula below.
- Rojo pipeline: known-good (`rojo build` after every change, no lint/type tooling installed).

## Plan

### Phase 1 — Trench arena rework

- `Arena.luau` — replace the two-platforms-across-a-gap layout with a trench sized from the
  block totals (see Open questions for the exact formula). This touches `GapWidth`,
  `PlatformSize`, block pile placement, the firing position(s), and likely `PrincessDistance`'s
  relationship to the new geometry — work out what stays a tunable and what's now derived.
- `Config.luau` — add whatever new trench constants are needed; keep everything derived from
  block totals computed once, not hardcoded twice.

### Phase 2 — Fixed weapon emplacements + turn-start selection

- Two fixed positions on the Attacker's side (`WeaponView.luau` currently has one `BASE`
  position — needs two).
- A selection step at the start of the Attacker's turn, before free aiming begins — new UI,
  wired into `AttackInput`/`init.client` alongside the phase transition into ATTACK.
- Settle whether `F` still exists as a mid-turn re-select (open question below).

### Phase 3 — Three-mode attack camera

- Default: top-down, engaged right after weapon selection.
- Toggle 1: first-person (`LockFirstPerson` — already proven in session 002).
- Toggle 2: 45°-down side view (re-derive the framing; the old scripted version isn't in the
  codebase to recover).
- A control to cycle or pick between the three (key TBD at Open Gate).

### Phase 4 — Re-tune targeting for the new geometry

- Recompute `MUZZLE_ORIGIN` for two emplacements instead of one.
- Verify the ballista's single-raycast aim and the catapult's wall-ignoring aim (both from
  session 002) still hold up at the trench's new distances and from all three camera modes —
  fix forward, don't just port the old numbers.

### Phase 5 — HUD / controls

- `Hud.luau` — reflect the turn-start selection step and the camera-toggle control in the
  Attacker's hint line.

## Open questions

Settle these at session start:

- **Trench height formula** — "as tall as the total height of the blocks": the literal sum of
  all 12 block heights stacked (`12 × 1.25 = 15` studs), or the tallest wall actually buildable
  under today's grid (spec's own reference build is "six-high," `6 × 1.25 = 7.5` studs)?
  Recommendation: the literal sum (15 studs) — it's what was asked for and it's a hard ceiling
  a real wall is unlikely to reach anyway, so it doesn't constrain build variety.
- **Trench width formula** — "as wide as their total cumulative width divided by 2": sum of
  every block's width (`6×2.5 + 6×7.5 = 60` studs) halved = **30 studs**. Recommendation: use
  this literal reading; flagging only because it's a new formula with no precedent in the
  codebase to check it against.
- **Does the weapon choice lock for the whole turn, or repeat per shot?** "The player starts
  their turn by selecting one or the other" reads as a one-time choice for all 6 shots.
  Recommendation: lock for the turn (simpler, matches the wording); drop the mid-turn `F`
  toggle entirely rather than keep it as a redundant path.
- **Camera default and toggle control** — recommend a single key (e.g. `C`) cycling
  top-down → first-person → 45°-side → top-down, defaulting to top-down on weapon selection.
  Confirm the key and the cycle order (or a dedicated key per mode instead).
- **Does `PrincessDistance` change with the trench, or stay independent?** Recommendation:
  keep it a separately-tuned Config constant (spec calls it "the single most important tuning
  value") — the trench formulas size the trench itself, not where the Princess stands inside
  it.

## Process rules

- Read every file you intend to modify before editing it.
- All game state and physics is server-authoritative. Clients send intent only; the server
  validates role, phase, and limits on every remote.
- Every tunable lives in `src/shared/Config.luau`. No gameplay magic numbers in logic.
- One ModuleScript per responsibility. `init.*.luau` scripts only bootstrap.
- `src/shared` never requires from `src/server` or `src/client`.
- Match the existing code style. No comments or type annotations on code you did not write.
- Adapt silently to small drift between this brief and the code; note it in one line. Pause
  and ask only for decisions that are expensive to reverse — data shape, new abstractions,
  changes to the arena or physics model.
- A question from the user is a question, not an instruction to act.
- When implementation is done: sync in Studio, run a two-player playtest, report what you
  saw. Then stop — do not start the close until the user says so.
