# Session 014 — Tune, Then Launch — Brief

**Roadmap section:** Pass 14 — Tune, then launch (`roadmap.md`)
**Branch:** session-014

## Goal

Systematically tune `Config` by feel across repeated two-player playtests — in the priority order
of roadmap §7, extended with the scoring and spin constants that postdate it — then publish the
place to Roblox and verify it actually plays in the real client outside Studio, per roadmap §8.
No new mechanics. This is the last pass on the roadmap; by the end the game should be both
balanced enough to be worth playing and reachable from a real Roblox client by a second account.

## Starting state

- Session 013 is implemented and playtested green: the catapult has real spin. `Config` gained
  `CatapultMaxSpin` (10 rad/s) and `CatapultMagnusCoefficient` (0.008 — an acceleration
  coefficient, not a raw force, so curvature stays mass-independent). `WeaponManager.fire()` takes
  a `spin` param, sets an initial `AssemblyAngularVelocity` about Y for the catapult, and attaches
  a per-frame `VectorForce` recomputed each Heartbeat from the ball's live velocity, removed on
  first `Touched` (airborne only). The ballista deliberately has no spin at all, preserving its
  flat-trajectory identity per spec.
- The launch meter is now a **three-stage, same-button sequence**: click 1 locks aim and starts
  the power meter (unchanged); click 2 freezes power — ballista fires immediately (unchanged),
  catapult instead opens a second, smaller meter above the power one that oscillates left-right
  continuously (looping triangle wave), its frequency scaling with how hard the power swing was
  (`SPIN_OSC_MIN_FREQ` 0.5 Hz → `SPIN_OSC_MAX_FREQ` 2 Hz); click 3 freezes spin and fires.
  Timeout behavior is deliberately asymmetric: power running out still **cancels** the shot;
  spin running out (`SPIN_TIMEOUT` 3s) still **fires**, pinned to full spin at the rightmost
  extreme.
- `AttackInput`'s predictive trace (`stepTrace`/`traceShot`/`showTrace`) takes an optional spin
  vector and applies the same per-step Magnus acceleration the server does, so the crosshair and
  dashed line curve in real time as the spin meter oscillates. `Types.ShotPayload` gained
  `spin: number`.
- Session 013's playtest was clean: "this works as expected and the game is starting to balance a
  bit." No bugs, nothing carried forward as unfinished. What it carried forward is **tuning debt**,
  which is this session's whole subject.
- Untuned or first-pass numbers inherited (nothing below has been independently tuned against a
  spread of outcomes):
  - Session 013: `CatapultMaxSpin` (10), `CatapultMagnusCoefficient` (0.008), `SPIN_OSC_MIN_FREQ`
    (0.5), `SPIN_OSC_MAX_FREQ` (2), `SPIN_TIMEOUT` (3).
  - Session 012 scoring: `BlockTopplingAngle` (60°), `PointsPerSurvivingBlock` (1),
    `PrincessKillPoints` (15, derived as `round(PieceCount * PieceMaxCells / 4)` = ~1/4 of the
    theoretical max wall score of 60).
  - Session 012 mid-session retunes: `CatapultProjectileMass` (43.75), `METER_LEG_TIME` (2.4s),
    `ShotSequence` (5 shots — `Catapult, Catapult, Catapult, Ballista, Ballista`).
- Current headline values to tune against: `PrincessDistance` 28, `GapWidth` 40, `BlockSize`
  3.75³, `BlockMass` 25, `BlockFriction` 0.5, `BlockRestitution` 0.1, `PieceCount` 10,
  `BallistaMinVelocity` 190 / `BallistaMuzzleVelocity` 320, `CatapultMinForce` 70 /
  `CatapultMaxForce` 120, `CatapultMinAngle` 15 / `CatapultMaxAngle` 50,
  `PrincessTopplingAngle` 78, `GroundFriction` 0.8 / `GroundRestitution` 0.05, `ShieldDuration`
  0.5, `GuardDistance` 22 (= `PrincessDistance - 6`), `RoundsPerMatch` 4.
- Rojo pipeline: known-good (`rojo build` after every change, no lint/type tooling installed).

## Plan

### Phase 1 — Set up the tuning loop

Before changing any number: run one baseline two-player playtest of the current build and write
down what actually feels wrong, in the user's words. Tuning without a stated complaint is
guesswork. Keep a running note through the session of every value changed, its old value, and the
observation that motivated it — the close-time log's "Config changes" section needs it, and so
does anyone re-reading `Config.luau` later, since every constant there carries a why-comment.

Change **one group at a time, then playtest**. Do not batch unrelated adjustments into a single
test round — sessions 009 and 012 both show how quickly that makes a result unattributable.

### Phase 2 — Tuning pass, in roadmap §7's priority order

§7's list predates sessions 012 and 013, so items 6 and 7 below are additions, not part of the
spec's original priority. Work top to bottom; the earlier items move the later ones, not the
reverse.

1. **`PrincessDistance`** (28) — the one value everything keys off. Target: a well-aimed catapult
   shot clears a short wall and reaches her, but a tall wall makes that arc genuinely difficult.
   Note that `PlatformSize` depth and `GuardDistance` both derive from it, so a change here moves
   the arena and the guard with it.
2. **`ShotSequence`** (5 shots) — the difficulty dial. Both length and composition are in play:
   more catapults favor breaking the wall, more ballistas favor finishing an exposed Princess.
   `ShotsPerTurn` derives from its length, so nothing else needs editing.
3. **Block mass + friction, and `BlockSize`/`PieceCount`** (25 / 0.5, 3.75³ / 10) — whether a base
   hit slides one piece out and drops the stack straight down, or blasts through and scatters it,
   and how much wall a single hit can plausibly remove. `BlockSize` drives `GridSize`,
   `PIECE_MAX_SPAN`, `BuildZoneSize` and the trench, so treat it as a heavier change than the
   others here and retest the BUILD phase after moving it.
4. **Ballista velocity range** (190–320), then **catapult force + angle range** (70–120,
   15°–50°), then each weapon's **projectile mass/friction/restitution**
   (`BallistaProjectileMass` 6, `CatapultProjectileMass` 43.75, and the two restitutions — 0.2
   and 0.45). Remember mass never changes trajectory under Roblox's drag-free gravity, only
   impact momentum — so use mass for "hits harder," velocity/force/angle for "lands elsewhere."
5. **`PrincessTopplingAngle`** (78) and **`GroundFriction`/`GroundRestitution`** (0.8 / 0.05)
   last, to taste — how hard she is to finish once exposed, and how long a landed ball rolls.
6. **Scoring constants** (added — session 012, never independently tuned):
   `PointsPerSurvivingBlock` (1), `PrincessKillPoints` (15), `BlockTopplingAngle` (60°). Tune
   these against a deliberate spread of outcomes, which session 012's own playtest never
   itemized: wall mostly intact, wall mostly destroyed, early Princess kill, late Princess kill.
   The question to answer is whether a Builder who defends well can actually out-score a
   successful Attacker, and vice versa — if one side always wins on points regardless of play,
   `PrincessKillPoints` is the lever. `BlockTopplingAngle` decides what counts as a piece that
   "survived," so check it against pieces that are visibly leaning but not down.
7. **Spin constants** (added — session 013, all first-pass guesses): `CatapultMaxSpin` (10) and
   `CatapultMagnusCoefficient` (0.008) in `Config`; `SPIN_OSC_MIN_FREQ` (0.5), `SPIN_OSC_MAX_FREQ`
   (2) and `SPIN_TIMEOUT` (3) in `AttackInput`. The feel target: spin should make the third click
   a real decision — enough curve to matter, not so much that a centered stop is the only viable
   choice and the meter becomes a formality. Frequency governs how hard that third click is;
   check the fast end is still hittable after a full-power swing. Keep the UI-feel constants local
   to `AttackInput` (the `ANGLE_STEP`/`METER_LEG_TIME` precedent) — only physics values go in
   `Config`.

Also fair game if a playtest calls for it, though not on §7's list: `METER_LEG_TIME` (2.4s),
`ShieldDuration` (0.5s), `GuardDistance`/`GuardSize`, and `RoundsPerMatch` (4).

A hard rule for this phase, straight from the spec: if one build strategy dominates, the fix is a
number here — never a new mechanic.

### Phase 3 — Confirm the spec's Definition of Done still holds

After tuning settles, run one clean full match end to end and check all six points of spec's
"Definition of done" still pass without outside instruction — roles visible, build and confirm,
the full shot sequence with correct weapons, the Princess dying correctly (including by falling
block), round resolve and role swap, and a winner declared after `RoundsPerMatch`. Tuning touches
mass, size and distance, all of which can break something that used to work; verify rather than
assume.

### Phase 4 — Publish to Roblox

Per roadmap §8, in this order:

1. **Stop the Rojo session first**, so no half-synced state ships. This is step 3 in §8 but it has
   to happen before the publish, not after.
2. In Studio: **File → Publish to Roblox As…**, name the place, create it.
3. **Home → Game Settings → Permissions** — Public to let anyone join, or keep it private and use
   Friends. Either is fine for a prototype; Friends is the smaller blast radius.

This phase is done by the user in Studio — the assistant's job is to walk the steps and confirm
each one landed, not to automate them.

### Phase 5 — Verify outside Studio

Open the published game from the Roblox client with a second account or a friend, and play at
least one full match. This is a real check, not a formality: physics network ownership and remote
behavior differ outside Studio's single-machine test, and this is the first time the build has
ever run across two actual machines. Specifically watch for:

- Blocks and projectiles simulating consistently for both players (everything is
  `SetNetworkOwner(nil)`'d server-side — confirm that holds up over a real network).
- The three-stage launch meter and the curving trace preview still tracking the real shot under
  latency — the client predicts locally, the server simulates authoritatively, and any divergence
  will be far more visible here than in Studio.
- HUD, result banner, shield activation, and the round/role swap all firing correctly for the
  remote client.

If something only breaks outside Studio, log it precisely — it's a genuinely new class of bug for
this project and there's no later pass currently scheduled to absorb it.

## Out of scope

- **New mechanics of any kind.** The roadmap's Pass 14 is tuning plus launch. If a playtest
  surfaces something that needs a mechanic rather than a number, write it down for a future pass
  rather than building it.
- The deferred structural-placement-rules item (roadmap §6) — explicitly not this session, still
  unscheduled.
- Menus, lobbies, matchmaking, persistence, currency, cosmetics, sound, particles, leaderboards,
  mobile controls, tutorial — all out per spec's "Explicitly out of scope," and publishing does
  not change that.
- Refactors. Tuning edits change values and their comments; leave structure alone.

## Open questions

Settle these at the Open Gate:

- **Permissions: Public or Friends.** §8 offers both. Friends is the safer default for a
  prototype with no moderation, menus, or onboarding; Public is only worth it if the user wants
  strangers to find it. Cheap to change later either way, but it should be a deliberate choice
  before publishing.
- **How much tuning before publishing.** The roadmap's order is tune, *then* launch — but the
  out-of-Studio test may itself change how things feel, and republishing is cheap. Worth
  confirming whether the user wants the tuning pass fully settled first, or a publish earlier so
  the real-client test can inform the last round of tuning.
- **Whether a second account/friend is actually available.** Phase 5 needs a second real client.
  If one isn't available this session, the publish still happens and Phase 5 carries forward —
  better to know that at the gate than at the end.

## Process rules

- Read every file you intend to modify before editing it.
- All game state and physics is server-authoritative. Clients send intent only; the server
  validates role, phase, and limits on every remote.
- Every tunable lives in `src/shared/Config.luau`. No gameplay magic numbers in logic.
- One ModuleScript per responsibility. `init.*.luau` scripts only bootstrap.
- `src/shared` never requires from `src/server` or `src/client`.
- Match the existing code style. No comments or type annotations on code you did not write.
- Adapt silently to small drift between this brief and the code; note it in one line. Pause
  and ask only for decisions that are expensive to reverse — data shape, new abstractions,
  changes to the arena or physics model.
- A question from the user is a question, not an instruction to act.
- When implementation is done: sync in Studio, run a two-player playtest, report what you
  saw. Then stop — do not start the close until the user says so.
