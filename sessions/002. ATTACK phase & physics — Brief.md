# Session 002 — ATTACK phase & physics — Brief

**Roadmap section:** Pass 2 — ATTACK phase + physics (`roadmap.md`)
**Branch:** session-002

## Goal

Implement the ATTACK phase end to end: on `ConfirmBuild` the wall unanchors and becomes
server-owned physics, the Attacker gets 6 shots and on each one chooses a weapon and aims,
projectiles are server-simulated, and blocks fall and topple under gravity and knockback.
The Princess is still an inert part — no kill detection this session. After 6 shots the state
machine holds.

## Starting state

- BUILD phase is complete and playtested green. `MatchController` assigns Builder/Attacker
  by join order, positions characters, broadcasts `StateChanged`, and on `ConfirmBuild`
  flips `phase` to `"ATTACK"` and just holds — no shot logic exists.
- Blocks: all 12 are pre-spawned as anchored `Part`s at match start (6 Standard
  `2.5×1.25×2.5`, 6 Wide `7.5×1.25×2.5`) in two piles on the builder's right, tagged with
  `BlockId` / `BlockType` / `Placed` attributes. `PhysicalProperties` are already applied
  (one density from `Config.BlockMass`, so a Wide block masses 3×). Rotated Wide blocks
  carry a 90° CFrame. Each block is its own assembly — no welds. `BlockManager` has
  `spawnAll` / `moveToWall` / `returnToPile` / `remainingByType` / `clear` but **no
  `releaseAll`**.
- `BuildManager` grid occupancy is authoritative during BUILD and simply goes stale at
  `ConfirmBuild` (blocks become physical, no longer grid-bound). Fine — leave it.
- Config: every ATTACK tunable already exists — `BallistaMuzzleVelocity` (320),
  `BallistaGravityScale` (0.05), `CatapultMinForce` (80), `CatapultMaxForce` (220),
  `CatapultMinAngle` (20), `CatapultMaxAngle` (70), `CatapultImpact` (60), `ShotsPerTurn`
  (6), `ProjectileLifetime` (5), `MovingBlockKillSpeed` (10, unused until Pass 3). Added
  this session: a muzzle-origin height, and a ballista knockback constant (see open
  questions).
- `Remotes` has `StartRequested` / `PlaceBlock` / `PickupBlock` / `ConfirmBuild` /
  `StateChanged`. No `FireWeapon`. `StateChanged` payload is
  `{ phase, roles, blocksRemaining = {Standard, Wide}, round }` — no `shotsRemaining` yet.
- `Types` has `Phase`, `Role`, `Weapon` (`"Ballista" | "Catapult"`), `ShotPayload`
  (`{ weapon, direction, force, angle }`), `StatePayload`. `StatePayload` needs
  `shotsRemaining`.
- Client: `Hud` shows role / phase / per-type blocks-remaining / a BUILD controls hint /
  the waiting line — nothing for ATTACK. `BuildInput` is builder-only and tears down when

- Rojo pipeline: known-good.
- Deferred from 001 (do not address here): structural placement rules (see `roadmap.md`

## Plan

### Phase 1 — Shared plumbing + wall release

- `Remotes.luau` — add `FireWeapon`.
- `Config.luau` — add the muzzle-origin height and the ballista knockback constant settled
  in the open questions. No other new numbers.
- `Types.luau` — add `shotsRemaining: number` to `StatePayload`.
- `BlockManager.luau` — add `releaseAll()`: for every block, `part.Anchored = false` then
  `part:SetNetworkOwner(nil)` (in that order — `SetNetworkOwner` errors on an anchored
  part). Handle un-placed pile blocks per the open-question decision.

### Phase 2 — WeaponManager (server)

- `src/server/WeaponManager.luau` — handle `FireWeapon` (validate: requester is the
  Attacker, `phase == "ATTACK"`, a shot is available). Spawn a server-owned projectile
  `Part` (create → unanchor → `SetNetworkOwner(nil)` → set initial
  `AssemblyLinearVelocity`). Step it on `Heartbeat`: apply gravity
  (`Config.BallistaGravityScale * workspace.Gravity * dt` for the ballista, full
  `workspace.Gravity * dt` for the catapult), raycast last-position → new-position, act on
  the first hit, despawn after `Config.ProjectileLifetime`.
  - Ballista: fixed speed `Config.BallistaMuzzleVelocity`, near-flat, direction straight
    from the aim. A standing block in the lane is hit first (no arc-over). Knockback per the
    open question.
  - Catapult: initial velocity from `force` (wheel, server-clamped to
    `CatapultMinForce..MaxForce`) + `angle` (Q/E, server-clamped to
    `CatapultMinAngle..MaxAngle`) + horizontal heading from `direction`. Full gravity. On a
    block hit, `block:ApplyImpulse(dir * Config.CatapultImpact)`, then the projectile
    despawns.
  - The server clamps or rejects out-of-range `force` / `angle`; the client value is a
    request.

### Phase 3 — Shot loop (server)

- `MatchController.luau` — on entering ATTACK (in `confirmBuild`): call
  `BlockManager.releaseAll()`, set `shotsRemaining = Config.ShotsPerTurn`, broadcast.
  Route each `FireWeapon` through `WeaponManager`, then decrement `shotsRemaining` and
  rebroadcast. At 0, hold — no RESOLVE, no SWAP, no round loop this session.
- `init.server.luau` — require and start `WeaponManager`.

### Phase 4 — AttackInput (client)

- `src/client/AttackInput.luau` — active only while `phase == "ATTACK"` and the local
  player is the Attacker. Mouse ray for aim direction; mouse wheel adjusts catapult force
  (clamped to Config range); `Q` / `E` adjust catapult angle (clamped); `F` toggles the
  active weapon; click fires `FireWeapon { weapon, direction, force, angle }`. A thin beam
  previews the aim (functional, not styled). Tear down cleanly when the phase leaves ATTACK.
  Push the current weapon / force / angle to `Hud` for the readout.
- `init.client.luau` — start `AttackInput` and feed it `StateChanged` alongside `Hud` and
  `BuildInput`.

### Phase 5 — HUD (attack readout)

- `Hud.luau` — during ATTACK show shots remaining (from `StateChanged`) and the active
  weapon + force/angle readout (from `AttackInput`). Minimal text, no sliders. Hide the
  BUILD counters/hint.

## Open questions

Settle these at session start:

- **Un-placed pile blocks at ATTACK start:** `releaseAll()` unanchors the wall. Blocks
  still sitting in the piles (never placed) should be — removed outright, left anchored, or
  released too and allowed to tumble? Recommendation: remove them; they aren't the wall and
  physics-active piles are clutter and an exploit surface.
- **Ballista knockback:** the spec says the ballista "removes foundations" and the pass's
  Done-when is "a base hit can topple a tall stack" — so a ballista hit must impart force to
  the block it strikes, not just despawn. Add a `BallistaImpact` constant, or reuse
  `CatapultImpact`? Recommendation: a separate `BallistaImpact`, starting equal to
  `CatapultImpact`, so the two can diverge in Pass 4 tuning.
- **Muzzle origin:** a fixed point derived from the Attacker's firing position plus a
  height constant (deterministic, server-authoritative regardless of where the avatar
  wandered), or tied to the Attacker's character/camera? Recommendation: fixed point +
  `MuzzleHeight` constant.

## Process rules

- Read every file you intend to modify before editing it.
- All game state and physics is server-authoritative. Clients send intent only; the server
  validates role, phase, and limits on every remote.
- Every tunable lives in `src/shared/Config.luau`. No gameplay magic numbers in logic.
- One ModuleScript per responsibility. `init.*.luau` scripts only bootstrap.
- `src/shared` never requires from `src/server` or `src/client`.
- Match the existing code style. No comments or type annotations on code you did not write.
- Adapt silently to small drift between this brief and the code; note it in one line. Pause
  and ask only for decisions that are expensive to reverse — data shape, new abstractions,
  changes to the arena or physics model.
- A question from the user is a question, not an instruction to act.
- When implementation is done: sync in Studio, run a two-player playtest, report what you
  saw. Then stop — do not start the close until the user says so.
