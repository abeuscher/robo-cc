# Session 005 — Irregular Blocks — L-Piece Pilot — Brief

**Roadmap section:** Pass 5 — Irregular Blocks (L-Piece Pilot) (`roadmap.md`) — inserted;
renumbers the old Pass 5 "Tune, then launch" to Pass 6.
**Branch:** session-005

## Goal

Replace the current 6 Standard + 6 Wide rectangular block roster with 12 identical L-shaped
four-cell pieces, and generalize the grid/placement/physics pipeline from "footprint = one
rectangle, 2-state flip" to "footprint = arbitrary multi-cell shape, full 4-state rotation."
This is an explicit test of whether irregular block shapes make the BUILD phase more
interesting — more shapes are expected to follow if it does, per this session's own scope.

## Starting state

- Session 004 (win/loss + full match) is implemented and playtested green — RESOLVE, SWAP,
  and best-of-4 all work end to end. This session is unrelated to that scope; it only touches
  the BUILD-phase block model. `src/client/BuildInput.luau` in particular has not been opened
  in any session since 001 — read it fresh, don't assume its shape from the roadmap summary.
- The current block model, precisely, before this session touches it:
  - `Config.BlockTypes` is a list of `{ Name, Size: Vector3, Count, Rotatable: boolean }` —
    one rectangle per type, two types (Standard, Wide).
  - `GridUtil.spanForSize(size, rotated)` + `coveredCells(anchor, span)` assume a single
    rectangular footprint; `rotated` is a boolean that only ever flips `Wide` between
    horizontal and vertical.
  - `BlockManager.makeBlock` spawns one plain anchored `Part` sized to `typeDef.Size`.
  - `BuildManager.onPlaceBlock`'s payload carries `rotated: boolean`
    (`Types.PlacePayload.rotated`).
  - None of this survives an L-piece unchanged — a footprint that isn't a rectangle and a
    rotation that isn't a flip touches all four of these.
- The following were settled in conversation before this brief was drafted (restated here so
  they don't need to be re-litigated at the Open Gate, only confirmed):
  1. **Placement stays physics-only.** No new placement-time support/floating validation —
     cells just need to be free and in-bounds, exactly like today. Stability is decided
     entirely by physics once `BlockManager.releaseAll()` unanchors everything at ATTACK
     start. Roadmap's "Deferred — structural placement rules" item stays deferred, untouched
     by this session.
  2. **Physical shape:** a `UnionOperation` of 4 standard block-cubes per L-piece — one
     `BasePart`, single rigid assembly, no `WeldConstraint`s.
  3. **Mass:** L-piece = 4× Standard's mass at equal density (the same density rule `Wide`
     already uses for its 3× volume).
  4. **Roster:** 12 L-pieces entirely replace the current 6 Standard + 6 Wide stock — not
     additive. `BlockManager`'s two-pile UI collapses to one pile.
  5. **Rotation:** full 4-state (0°/90°/180°/270°), not the current single-flip boolean.
- Rojo pipeline: known-good (`rojo build` after every change, no lint/type tooling installed).

## Plan

### Phase 1 — Shape model (shared)

- `Config.luau` — replace the two-type roster with one L-piece type defined as a **shape**: a
  list of local grid-cell offsets at rotation 0 (three cells in a row, one hanging off the
  bottom of one end — see Open Questions for the exact offsets), plus the existing
  `BLOCK_SIZE` for the sub-cube dimensions, `Count = 12`.
- `Types.luau` — `PlacePayload.rotated: boolean` → `PlacePayload.rotation: number` (0-3,
  quarter turns).
- `GridUtil.luau` — add shape-rotation math: rotate a cell-offset list by `rotation`
  quarter-turns about the shape's own anchor; `coveredCells` takes a shape + anchor +
  rotation instead of a rectangular span. `isInside` and `cellToWorld` stay as they are —
  they already operate per-cell, not per-footprint.

### Phase 2 — `BlockManager.luau` — compound part

- Build each L-piece as a `UnionOperation` of 4 sub-cubes at spawn, sized/positioned from the
  shape definition and `Config.BlockSize`.
- Same density-based `PhysicalProperties` formula, applied to the union (a `UnionOperation` is
  a `BasePart` and takes `CustomPhysicalProperties` the same way a `Part` does).
- `moveToWall` / `returnToPile` keep operating on the union's `CFrame`, just rotated by a
  quarter turn instead of the old ±90° flip.
- `releaseAll` / `SetNetworkOwner` unchanged — same `BasePart` API either way.

### Phase 3 — `BuildManager.luau` — placement validation

- `onPlaceBlock` walks the shape's covered cells via the new `GridUtil` shape API instead of a
  rectangular span; occupancy/bounds checks stay conceptually the same, just iterating a
  different cell list.
- `rotated: boolean` → `rotation: number`, validated and clamped to 0-3.

### Phase 4 — Client — ghost + rotation

- `BuildInput.luau` — ghost preview draws the L-shape's actual cells (not a bounding
  rectangle — see Open Questions), `R` cycles all 4 rotations instead of toggling a flip.
- `Hud.luau` — update the BUILD hint line if the rotate control's description no longer
  matches (still `R`, just a full cycle now).

### Phase 5 — Playtest

Two-player Studio playtest: 12 L-pieces show up in a single pile, placement snaps correctly
at all 4 rotations, occupancy/bounds validation holds, and unanchoring at ATTACK start
produces a real physical stability test — an unsupported overhang should visibly topple or
settle under gravity rather than floating.

## Open questions

Settle these at session start:

- **Exact L-piece geometry.** "Three cells in a row, one hanging off the bottom of one end" —
  confirm as offsets in (column, row) grid units at rotation 0, e.g.
  `(0,0), (1,0), (2,0), (0,-1)` (the extra cell hangs below the row's left end). Which end,
  precisely, and is "hangs below" the intended direction (vs. above)?
- **Union attributes.** The placed L-piece should carry a single `BlockId` / `BlockType`
  attribute on the union root, same as today's single-part blocks — this should just work
  unchanged since a `UnionOperation` is one `BasePart`, but confirm there's no sub-part-level
  attribute surprise (this also matters for `PrincessMonitor`'s `Touched` handler, which reads
  `BlockId` off whatever part touches the Princess).
- **Ghost fidelity.** Does the client draw the ghost as 4 translucent unit cubes matching the
  real shape, or is a simplified bounding-box ghost acceptable for this pilot? Recommend the
  real per-cell ghost — a bounding box would misrepresent the actual footprint, which
  undercuts the point of testing an irregular shape.
