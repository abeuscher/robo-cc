# Session 016 — Two-Button Meters & Ballista Elevation — Brief

**Roadmap section:** Pass 16 — Two-Button Meters & Ballista Elevation (`roadmap.md`)
**Branch:** session-016

## Goal

Replace the launch sequence's third stage — currently a catapult-only meter that oscillates on its
own until a click freezes it — with a fixed 3-second window in which the Up/Down arrow keys steer a
dot, shared by both weapons, and use that new stage to give the ballista a real elevation axis for
the first time. The meters also move to the left of the Attacker's screen and stay up for the whole
turn instead of appearing mid-swing.

## Starting state

- **The meters are entirely `AttackInput`'s.** They live in their own `ScreenGui` named
  `LaunchMeter`, built by `makeMeter()` and `makeSpinMeter()` and shown/hidden by
  `AttackInput.update()`. `Hud.luau` owns only the bottom-right info panel (weapon icon, angle
  readout, hints) and the top-right score panel, and never touches them. So Pass 16's "HUD
  relayout" is an `AttackInput`-internal GUI change; `Hud.luau` is touched only for the hint text.
- **Current third stage (session 013).** `stage` runs `"idle"` -> `"power"` -> `"spin"` -> back to
  `"idle"`. `beginSpinStage()` starts a free-running `triangleWave()` oscillator whose frequency
  interpolates `SPIN_OSC_MIN_FREQ` (0.5 Hz) to `SPIN_OSC_MAX_FREQ` (2 Hz) by the *locked power
  fraction* — a deliberate difficulty coupling (a big power swing makes the spin harder to land).
  A third click calls `freezeSpinAndFire()`; letting it run past `SPIN_TIMEOUT` (3s) fires anyway,
  pinned to full spin at the right extreme. **Nothing in the new design replaces that power
  coupling** — a fixed window is equally easy at any power. That's an intentional loss to
  acknowledge, not overlook (see Open questions).
- **The ballista has no third stage at all.** `freezePowerAndAdvance()` branches on the locked
  weapon: catapult into `beginSpinStage()`, ballista straight into `fireLockedShot(0)`.
  `fireLockedShot()` then hardcodes `angle = if weapon == "Catapult" then angle else 0`, and
  `WeaponManager.launchVelocity()`'s `Ballista` branch returns `heading * speed` with no vertical
  component — the shot is dead flat by construction on both sides of the wire.
- **Nothing enforces "cannot arc over" as a rule.** The spec line is emergent, not coded: since
  session 009 both weapons are ordinary physics balls, and a wall blocks the ballista only because
  a flat shot fired from `Config.MuzzleHeight` (0.75) physically runs into it. There is no blocking
  flag to keep or remove — the Open Gate question below is therefore purely "how large a range",
  with no second mechanism to decide.
- **Layout today.** `LaunchMeter`'s `Track` is `28x320` px anchored to the **right** edge
  (`UDim2.new(1, -36, 0.5, 0)`); `SpinTrack` is a `110x16` strip positioned off that track's top
  edge, `Visible = false` until power freezes. The whole gui is enabled on the ATTACK/Attacker
  transition, but the fill only animates during a swing and the spin strip only appears mid-swing.
- **Config vs. local constants — the standing precedent.** Gameplay-balance tunables live in
  `Config` (`CatapultMinAngle`/`MaxAngle` 15/50, `CatapultMaxSpin` 10, `CatapultMagnusCoefficient`
  0.008, `BallistaMinVelocity`/`BallistaMuzzleVelocity` 190/320); pure UI-feel constants have
  stayed local to `AttackInput` (`ANGLE_STEP` 5, `METER_LEG_TIME` 2.4, the three spin-meter
  constants — session 013's log records this split explicitly). Sort the new constants the same
  way: the ballista's elevation range is balance and goes in `Config`; the window duration and the
  dot's travel rate are feel and stay local. There is no ballista elevation constant of any kind in
  `Config` today.
- **`Up`/`Down` are genuinely unused by this game** — the only bound keys anywhere in `src/client`
  are `Q`/`E` (angle), `R`/`Z` (build), `C` (camera), `F` (shield). They are *not* unused by
  Roblox: the arrow keys are part of the default character-movement bindings and the Attacker's
  character is a normal walking humanoid, so a plain `InputBegan` binding will move the character
  as well as the dot. Also note `InputBegan` is edge-only — "continuously while held" means polling
  `UserInputService:IsKeyDown` from the existing `RenderStepped` handler, not counting presses.
- **Session 015's Flag work lives in this same file and is unrelated to this pass.**
  `AttackInput.luau` now also owns Attacker-only Flag concealment: the `flagRevealed` local,
  `applyFlagConcealment()` (called from `AttackInput.update()` on *every* `StateChanged`, not just
  the active/inactive transition), the `flagPart()` helper, and the hidden-Flag exclusions inside
  both `traceParams()` and `catapultAimPoint()`'s raycast filters. Rewriting the input state
  machine around it must not disturb any of it — in particular, the trace calls this session
  rewires still have to go through `traceParams()` rather than building their own
  `RaycastParams`, or the crosshair will start leaking the hidden Flag's position.
- Elsewhere in the codebase, session 015 (finished, not yet closed) replaced the Princess with a
  hidden Flag plus `src/server/FlagMonitor.luau`, added a POSITION phase for Flag relocation, added
  the rainbow wall palette, removed the Guard, and kept the Builder's timed Shield now tracking the
  Flag's live position. Context only — none of it is in scope here.
- Rojo pipeline: known-good as of session 015 (confirm with a build after the first edit anyway,
  per process rules).

## Plan

### Phase 1 — Config and shared types

Add the ballista's elevation range to `Config` (whatever the Open Gate settles — most likely a
`BallistaMinAngle`/`BallistaMaxAngle` pair mirroring the catapult's own naming, so
`launchVelocity()` can clamp it the same way it clamps the catapult's). Update `Types.ShotPayload`'s
documentation of `angle` so it's no longer catapult-only. The window duration and dot travel rate
stay local to `AttackInput`, per the precedent above.

### Phase 2 — Rework the third stage into a timed two-button window

Replace `stage == "spin"` and its oscillator with one timed window shared by both weapons: a fixed
3-second countdown (displayed 3-2-1 to the meter's right), Up/Down held to move the dot
continuously off its rest position, the window expiring to an auto-fire at whatever the dot reads —
which, untouched, is centred/flat, i.e. no spin and no elevation. This keeps session 013's
asymmetric timeout rule (the third stage fires rather than cancels; the power stage still cancels)
while removing what made it feel arbitrary: pinning to a full-right extreme becomes resting at
zero. `triangleWave()`, `SPIN_OSC_MIN_FREQ`, `SPIN_OSC_MAX_FREQ` and `beginSpinStage()`'s
power-fraction scaling all go away with it. Bind the keys so they don't also walk the character
(`ContextActionService` with a sink, or an equivalent), and drive movement from the render loop,
not from key-down events.

The catapult's own visualization becomes a single horizontal line with a dot that starts centred and
moves above or below it — above/below standing in for the same left/right curve direction the old
oscillating meter produced. The live predictive trace (`showTrace` with the current spin value)
should keep tracking the dot exactly as it tracked the oscillator, so the curve preview stays honest.

### Phase 3 — Ballista elevation, end to end

The same window for the ballista, visualized as a flat horizon line with a fulcrum and a second
segment that lifts off it as Up is held — roughly a "less than" shape once elevated, starting flat.
Then wire the value all the way through: `fireLockedShot()` stops zeroing `angle` for the ballista,
`WeaponManager.launchVelocity()`'s `Ballista` branch gains a vertical component clamped into the new
`Config` range, and `AttackInput`'s own `ballistaVelocity()` — which exists specifically to mirror
that branch for the predictive trace — gains the identical math so the dashed line and crosshair
still match where the shot really goes. The server clamps regardless of what the client sends, same
as it already does for force, angle and spin.

### Phase 4 — Meter relayout

Move the `LaunchMeter` gui to the left side of the Attacker's screen and keep both meters visible
for the whole turn rather than only mid-swing: the spin/elevation meter sits at its rest position
(centred dot / flat horizon) from the start of the turn, so its final position is never a surprise
the first time a player sees it. Double the power track in both height and width (`28x320` ->
`56x640`), leaving `METER_LEG_TIME` at 2.4 untouched — the bar then covers twice the distance in
the same time, which reads as faster without moving a constant other behaviour keys off. Check the
doubled track against a small viewport; 640px of track plus the countdown needs to survive a short
window. Update the Attacker's hint string in `Hud.luau` to describe the new sequence.

### Phase 5 — Playtest and verify

Two-player playtest covering both weapons end to end: catapult spin still curves the shot and the
trace still tracks it; the ballista elevates, and a raised shot behaves the way the Open Gate
decision says it should against a standing wall; an untouched window auto-fires flat/straight for
both; the meters are readable on the left for the entire turn; and the Flag still stays concealed
from the Attacker (crosshair and dashed line included) through the rewritten input path.

## Open questions

Settle these at the Open Gate:

- **How much arc does the ballista actually get?** This is the pass's real design decision, and
  `roadmap.md` explicitly leaves it here. Since blocking is emergent (see Starting state) the
  question is entirely "what's the maximum angle", with no separate rule to write either way. Three
  concrete options:
  1. **Shallow (roughly 0-8°).** Enough to clear rubble, a low surviving row, or the lip of a
     partly-collapsed wall at the 40-stud gap, but never a wall built to any real height. Spec
     identity fully preserved; the new axis is a precision tool for finishing a flattened wall
     rather than a way around a standing one.
  2. **Moderate (roughly 0-20°).** A genuine lob that can clear a short wall but not a tall one —
     the same "short wall yes, tall wall difficult" tension `spec.md` already asks the catapult's
     distance tuning to produce, now applied to the ballista too. Softens the spec line without
     erasing it, and makes the Builder's height-vs-thickness tradeoff matter against both weapons.
  3. **Full second axis (up to the catapult's own `CatapultMinAngle`, 15°, or beyond).** Treats
     "cannot arc over" as superseded, the way session 007 superseded spec's free weapon choice —
     an explicit, logged override. The risk is that the two weapons stop reading as different
     things, since after session 009 their only remaining distinctions are speed, mass and the
     catapult's spin.
  Option 2 is the recommendation if no strong preference: it's the one that changes how the wall is
  built rather than just how the last shot is aimed, and the range is a single `Config` value to
  retune afterwards.
- **Does Down do anything for the ballista?** Either it only un-lifts back toward flat (flat is the
  floor of the range, matching the "lifts off the horizon" visualization), or it depresses below
  flat, which at this muzzle height mostly means burying the shot in the ground short of the wall.
  The former is simpler and is assumed unless decided otherwise; say so either way, since the
  `Config` range's lower bound encodes the answer.
- **Does anything replace session 013's power coupling?** The oscillator's frequency scaling by
  locked power was a deliberate difficulty gradient, and a fixed 3-second window has none. Options:
  accept the loss (the window is a fairness/readability improvement and the mechanic doesn't need a
  penalty attached), or re-ground it — e.g. shorten the window as locked power rises, so a
  full-power swing gives less time to set the dot. Cheap to decide now, awkward to retrofit once
  the countdown UI exists.
- **Dot mapping.** Confirm that full deflection equals the full configured extreme
  (`Config.CatapultMaxSpin` for the catapult, the new max angle for the ballista) and that the dot
  resets to rest between shots within a turn rather than holding the previous shot's value.

## Process rules

- Read every file you intend to modify before editing it.
- All game state and physics is server-authoritative. Clients send intent only; the server
  validates role, phase, and limits on every remote.
- Every tunable lives in `src/shared/Config.luau`. No gameplay magic numbers in logic.
- One ModuleScript per responsibility. `init.*.luau` scripts only bootstrap.
- `src/shared` never requires from `src/server` or `src/client`.
- Match the existing code style. No comments or type annotations on code you did not write.
- Adapt silently to small drift between this brief and the code; note it in one line. Pause
  and ask only for decisions that are expensive to reverse — data shape, new abstractions,
  changes to the arena or physics model.
- A question from the user is a question, not an instruction to act.
- When implementation is done: sync in Studio, run a two-player playtest, report what you
  saw. Then stop — do not start the close until the user says so.
