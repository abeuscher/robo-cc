# Session 011 — Builder's Timed Shield — Brief

**Roadmap section:** Pass 11 — Builder's Timed Shield (`roadmap.md`)
**Branch:** session-011

## Goal

Give the Builder one active ability during ATTACK: a once-per-round, ~half-second protective
shield the Builder times themselves against an incoming shot, rather than a passive fixture.
This is the first piece of Builder agency after `ConfirmBuild` — today the Builder is pure
spectation from BUILD's end until the round resolves.

## Starting state

- Session 010 is implemented: a fixed, server-spawned `Guard` part (`Arena.build()`/
  `resetRound()`/`releaseGuard()`) sits between the wall and the Princess, unanchored into real
  physics at ATTACK start alongside the wall and the Princess, with no special-cased durability —
  it behaves exactly like a wall block. Playtested; user's assessment was "Better."
- The Builder currently has no input path at all once `ConfirmBuild` fires. `BuildInput` goes
  inactive on the BUILD→ATTACK transition (mirroring how `AttackInput` only activates for the
  Attacker); nothing takes its place for the Builder during ATTACK/RESOLVE.
- `PrincessMonitor`'s kill condition is a continuous tilt check (`Config.PrincessTopplingAngle`),
  contact-agnostic — it doesn't care what caused the tip, only whether it happened. A shield that
  works by being a real solid object in the way needs no changes to `PrincessMonitor` itself.
- The round loop (`MatchController`) already has a registration hook for per-round cleanup
  (`onRoundReset`), used by `BlockManager.resetQueue()` and `WeaponManager.clearAll()` — the
  shield's one-use-per-round flag should reset the same way.
- Rojo pipeline: known-good (`rojo build` after every change, no lint/type tooling installed).

## Plan

### Phase 1 — `Config` and the network contract

Add tunables: shield duration (~0.5s per the roadmap, first-pass guess like everything else),
shield size/shape, and anything else the chosen mechanism needs. Add `ActivateShield` to
`Remotes.EVENT_NAMES`. Decide whether `StatePayload` needs a shield-availability field for the
HUD (e.g. `shieldAvailable: boolean`) or whether the client can track "already used this round"
locally from its own fire-and-forget request — server stays authoritative either way.

### Phase 2 — Server: own the shield

Build whichever server-side module owns: validating `ActivateShield` (Builder role, ATTACK phase,
not already used this round), spawning the shield object, and despawning it after its duration.
Register the one-use flag's reset with `MatchController.onRoundReset`, the same pattern
`BlockManager`/`WeaponManager` already use.

### Phase 3 — Client: Builder input during ATTACK

A new input module (or an extension of an existing one) that activates only for the Builder
during ATTACK, listens for a key press, and fires `ActivateShield`. Mirror `AttackInput`'s
activate/deactivate pattern (connect on the phase+role transition in, disconnect on the way out).

### Phase 4 — HUD

Show the Builder whether the shield is still available, during ATTACK. Exact placement/wording is
a judgment call — match `Hud`'s existing style for role-specific readouts.

### Phase 5 — Playtest

Two-player Studio playtest: confirm the Builder can activate the shield exactly once per round
during ATTACK, that a well-timed activation physically blocks a shot that would otherwise land,
that a mistimed one does nothing useful, and that no shield part lingers between rounds.

## Out of scope

- Multiple uses or a cooldown-based refresh — roadmap specifies once per round.
- Any Attacker-side counterplay or feint mechanic against the shield.
- Pass 12 (scoring/points) and Pass 13 (weapon spin/trajectory) — separate sessions.
- Visual polish beyond a plain, readable shape for the shield object itself.

## Open questions

Settle these at the Open Gate:

- **Shield mechanism.** A real, solid, briefly-anchored object that physically blocks whatever
  hits it for its duration (consistent with the project's running move away from scripted hit
  rules — real projectiles, a real Princess, a real guard piece), or a scripted brief invulnerability
  window on `PrincessMonitor`'s tilt check (simpler, no new physical object, but reintroduces
  exactly the kind of special-cased rule sessions 009-010 moved away from)? Leaning toward the
  physical object.
- **If physical: anchored or not.** A timed shield probably needs to stay anchored for its whole
  duration — if it were a normal unanchored body like the guard, a heavy catapult hit could shove
  the shield itself into the Princess and defeat the purpose. This is a deliberate exception to
  "everything is real physics" for the shield specifically, worth confirming rather than assuming.
- **Does the Builder need a camera during ATTACK to time this at all?** Right now the Builder has
  no dedicated view of the trench once BUILD ends. A reactive, half-second-window ability is hard
  to time blind. Options: add a spectator-style camera for the Builder during ATTACK (new client
  work, likely bigger than the rest of this session combined), or accept a best-guess/blind
  activation for this first pass and revisit if playtesting shows it's unusable. Leaning toward
  the latter for a first pass, but flagging since it changes how much this session actually builds.

## Process rules

- Read every file you intend to modify before editing it.
- All game state and physics is server-authoritative. Clients send intent only; the server
  validates role, phase, and limits on every remote.
- Every tunable lives in `src/shared/Config.luau`. No gameplay magic numbers in logic.
- One ModuleScript per responsibility. `init.*.luau` scripts only bootstrap.
- `src/shared` never requires from `src/server` or `src/client`.
- Match the existing code style. No comments or type annotations on code you did not write.
- Adapt silently to small drift between this brief and the code; note it in one line. Pause
  and ask only for decisions that are expensive to reverse — data shape, new abstractions,
  changes to the arena or physics model.
- A question from the user is a question, not an instruction to act.
- When implementation is done: sync in Studio, run a two-player playtest, report what you
  saw. Then stop — do not start the close until the user says so.
