## Starting state

- BUILD and ATTACK are both complete and playtested (sessions 001–003). The Attacker fires
  through `shotsRemaining` down to 0 and the machine currently just holds there — no
  `PrincessMonitor`, no RESOLVE, no SWAP, no round loop. There is only ever one round.
- **`Remotes.luau` is missing `RoundResult` and `MatchResult`** — `roadmap.md` §3 documents
  their payloads but `EVENT_NAMES` only has `StartRequested`, `PlaceBlock`, `PickupBlock`,
  `ConfirmBuild`, `FireWeapon`, `StateChanged`. Both need adding, and `Types.luau` needs their
  payload shapes (it currently defines `Phase`/`Role`/`ShotPayload`/etc. but not these two).
- **The Princess is inert.** `WeaponManager.onHit` only acts on parts carrying a `BlockId`
  attribute; a projectile or a falling block can pass straight through the Princess part today
  with no effect. Both spec kill paths (direct projectile hit, contact with any moving block —
  including the Builder's own wall, no owner check) still need building from scratch.
- **Arena reset is not round-safe yet.** `Arena.build()` calls `Arena.reset()` (which does
  `root:ClearAllChildren()` on `Workspace.ActiveRound`) and then rebuilds *everything* — ground,
  boundary walls, all markers, piles, and the Princess — in one pass. It's only ever called once,
  at server start. `roadmap.md`'s own game-loop pseudocode calls `Arena.reset()` and
  `Arena.spawnPrincess()` as separate per-round steps, which the current code can't do: calling
  `Arena.reset()` mid-match would destroy the session-003 ground/boundary along with the blocks
  and Princess, and there's no lighter "just respawn the round-mutable stuff" path. This session
  needs to split static one-time geometry (ground, walls, markers, piles) from what actually
  resets each round (Princess position, `BlockManager`'s blocks via the existing `spawnAll()`,
  clearing any live projectiles). Flagging this now since it's the one piece of session 003's
  work this pass has to build on carefully rather than assume.
- **`BlockManager.spawnAll()` already exists** and is reusable as the per-round block respawn —
  it clears and re-spawns every configured block into its pile from scratch.
- **`MovingBlockKillSpeed` (`10`) is already in `Config`**, unused until `PrincessMonitor` reads
  it. No other kill-related tunables exist yet — this session likely adds one for the RESOLVE
  phase's settle delay (see Open questions).
- Rojo pipeline: known-good (`rojo build` after every change, no lint/type tooling installed).

## Plan

### Phase 1 — Shared plumbing

- `Remotes.luau` — add `RoundResult`, `MatchResult`.
- `Types.luau` — add their payload types per `roadmap.md` §3 (`RoundResult: { winner: Role,
  reason: "survived" | "direct" | "crushed" }`, `MatchResult: { winner: UserId?, score }`).
- `Config.luau` — whatever new tunable the RESOLVE settle delay needs (see Open questions).

### Phase 2 — `PrincessMonitor.luau` (server, new)

- Direct hit: a projectile raycast landing on the Princess part.
- Moving-block hit: `Touched` by any part tagged `BlockId` whose
  `AssemblyLinearVelocity.Magnitude > Config.MovingBlockKillSpeed` — no owner check, a
  Builder's own wall counts.
- Exposes whatever `MatchController` needs to poll or subscribe to (`isDead()` / a reason, per
  the roadmap's existing sketch).

### Phase 3 — Arena reset split

- Separate `Arena.build()`'s one-time static geometry (ground, boundary, markers, piles) from a
  new per-round reset path that repositions the Princess and clears live projectiles without
  touching the static parts.
- Wire `BlockManager.spawnAll()` into that same per-round reset.

### Phase 4 — Round loop (`MatchController.luau`)

- RESOLVE: once `shotsRemaining` hits 0 or `PrincessMonitor` reports a kill, wait a short settle
  beat for physics, then decide the round winner and broadcast `RoundResult`.
- SWAP: flip `roles.builder`/`roles.attacker`, reset the arena and blocks (Phase 3), grant a
  fresh block budget, return to BUILD.
- Score tracking across `RoundsPerMatch` (4); after the last round, broadcast `MatchResult`
  (winner = higher score, or no winner on a tie — spec: "tie is acceptable").

### Phase 5 — HUD / client

- `Hud.luau` — round score, and a round-result / match-result readout.
- `init.client.luau` — wire whatever new client module the result banner needs (if any).

## Open questions

Settle these at session start:

- **RESOLVE settle delay** — how long to wait after the last shot (or a kill) before deciding
  the round, so blocks/Princess physics can settle. Recommend a fixed `Config.ResolveSettleTime`
  (e.g. `1.5` seconds), exposed as a tunable rather than hardcoded.
- **Arena build/reset split** — confirm the approach in Starting State (static geometry built
  once, a separate lighter per-round reset for Princess/blocks/projectiles) rather than any
  alternative shape.
- **Tie handling** — `MatchResult.winner` as `UserId?`, per `roadmap.md` §3, already reads as
  "nil on a tie." Confirm no extra tie-specific message/state is expected beyond that.

## Process rules

- Read every file you intend to modify before editing it.
- All game state and physics is server-authoritative. Clients send intent only; the server
  validates role, phase, and limits on every remote.
- Every tunable lives in `src/shared/Config.luau`. No gameplay magic numbers in logic.
- One ModuleScript per responsibility. `init.*.luau` scripts only bootstrap.
- `src/shared` never requires from `src/server` or `src/client`.
- Match the existing code style. No comments or type annotations on code you did not write.
- Adapt silently to small drift between this brief and the code; note it in one line. Pause
  and ask only for decisions that are expensive to reverse — data shape, new abstractions,
  changes to the arena or physics model.
- A question from the user is a question, not an instruction to act.
- When implementation is done: sync in Studio, run a two-player playtest, report what you
  saw. Then stop — do not start the close until the user says so.
