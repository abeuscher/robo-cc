# Session 008 — Randomized Piece Generation — Brief

**Roadmap section:** Pass 8 — Randomized Piece Generation (`roadmap.md`)
**Branch:** session-008

## Goal

Replace the fixed 12-piece L-shape roster with a per-placement randomly generated shape: each
of the Builder's pieces fills 3-6 of the 9 cells in a 3×3 area at random (both the count and
which cells are randomized). Cells that end up mutually edge-adjacent fuse into one rigid
`UnionOperation`, exactly as today; cells that end up isolated from every other cell in the
piece stay independently physical instead of being forced into one body. This breaks the
invariant every prior BUILD-phase pass has relied on — one placed piece has always been
exactly one rigid assembly — so a single placement now has to resolve into however many
separate falling bodies its random connectivity produces at ATTACK start.

## Starting state

- Session 007 (fixed shot sequence) is implemented and playtested green.
- The current BUILD model, precisely, before this session touches it:
  - `Config.BlockTypes` is a one-entry list (`LPiece`, `Shape = L_SHAPE`, `Count = 12`);
    `Config.BlockCount` sums `.Count` across it (currently unused elsewhere — safe to repurpose
    or drop). `TOTAL_BLOCK_WIDTH`/`TOTAL_BLOCK_HEIGHT`, which size the trench
    (`BuildZoneSize`), are also summed from each type's static `.Size`.
  - `BlockManager.resetQueue()` flattens `Config.BlockTypes` into a queue of *type defs*
    (`{Name, Shape, Size, Count}`); `currentTypeDef()`/`remainingCount()` expose queue state
    keyed by type name; `placeCurrent()` builds one `UnionOperation` from the *entire* shape's
    cells, unconditionally.
  - `BuildManager.onPlaceBlock` reads `typeDef.Shape`/`.Name` off `currentTypeDef()`.
  - `MatchController.initialRemaining()` builds `{ [typeDef.Name] = typeDef.Count }` from
    `Config.BlockTypes`; `StatePayload.blocksRemaining` is that per-type-name table.
  - `BuildInput.luau` reads the held piece's shape from a **static** `Config.BlockTypes[1].Shape`
    constant (its own comment already flags this as provisional, pointing at "session 007" —
    stale from before the shot-sequence work took that slot at session 006's close; it means
    this session, not 007).
  - None of this survives random per-piece generation unchanged: the shape stops being a
    `Config`-resident constant the client can read for itself and becomes a runtime fact only
    the server knows, which has to reach the client the same way session 007 made the mandated
    weapon reach it — via the broadcast state, not a shared constant.
- Rojo pipeline: known-good (`rojo build` after every change, no lint/type tooling installed).

## Plan

### Phase 1 — `Config`

- Replace `BLOCK_TYPES`/`L_SHAPE` with generation parameters: a `PieceGridSize = 3` (3×3 cell
  area), `PieceMinCells = 3`, `PieceMaxCells = 6`, and `PieceCount = 9` (roadmap's already-decided
  figure — not re-tuned here, tuning stays Pass 9).
- `BuildZoneSize`'s derivation can no longer sum a fixed per-type `.Size` (there is no static
  size to sum). Rework it off `PieceCount` and `PieceMaxCells` (worst-case cells per piece) so
  the trench is always big enough regardless of what a given round's randomization produces —
  see Open Questions below.

### Phase 2 — `BlockManager` — generate instead of look up

- Add shape generation: pick a random cell count in `[PieceMinCells, PieceMaxCells]`, then pick
  that many distinct cells from the `PieceGridSize × PieceGridSize` grid, normalized the same
  way `GridUtil.normalizeShape` already normalizes rotated/mirrored shapes.
- `resetQueue()` builds this round's `PieceCount` shapes once, up front, same as today's
  flatten-from-`BlockTypes` timing — just generated instead of looked up. `currentTypeDef()`
  becomes `currentShape()` (no type name to carry).
- `placeCurrent()` splits the (possibly mirrored) shape into its edge-connected components
  before building: each component of 2+ cells becomes one `UnionOperation` as today; a
  component of exactly 1 cell is placed as a plain `Part` sized `Config.BlockSize` (a
  `UnionOperation` of one part has no reason to exist). Every component gets its own `BlockId`
  and lands in `placedParts`, so `releaseAll()` needs no change — it already just walks
  `placedParts` unconditionally.

### Phase 3 — `BuildManager` / `MatchController` — plain counts, no type names

- `onPlaceBlock` reads the shape from `BlockManager.currentShape()` instead of a type def; the
  occupancy/bounds validation against `GridUtil.coveredCells` is unaffected — it only ever
  consumed a cell list, never a type name.
- `MatchController.initialRemaining()`/`StatePayload.blocksRemaining` drop the per-type-name
  table for a single remaining-piece count, since there's now exactly one (unnamed, unbounded)
  piece kind.

### Phase 4 — `Types`

- Drop the `BlockType = "LPiece"` alias — nothing is named anymore.
- `BlocksRemaining` becomes a plain `number`.
- Add a shape type (e.g. `PieceShape = { Vector2 }`) and a `currentShape: PieceShape?` field on
  `StatePayload` — `nil` outside BUILD — so the client learns the held piece's shape from the
  broadcast instead of a shared constant, the same pattern session 007 used for the mandated
  weapon.

### Phase 5 — `BuildInput` / `Hud`

- `BuildInput` drops the static `PIECE_SHAPE` constant; `baseShape()` mirrors
  `StateChanged.currentShape` instead, updated on every `StateChanged` while active (a fresh
  piece arrives after every placement, well inside a single BUILD phase — same "update on every
  broadcast, not just on activation" shape session 007 needed for weapon).
- `Hud`'s blocks-remaining readout reads the plain count instead of `.LPiece`.

### Phase 6 — Playtest

Two-player Studio playtest: each of the 9 pieces is a freshly randomized shape (verify by eye
that no two look alike across a full round), all 4 rotations and the mirror flip still work on
an irregular/disconnected shape, placement/occupancy correctly rejects a shape that would run
off the grid, and at ATTACK start a piece with isolated cells drops each cluster independently
rather than as one rigid body.

## Open questions

- **What assumption should size the fixed trench (`BuildZoneSize`)?** The trench is built once
  as static geometry — it can't resize itself round to round — but per-piece cell count is now
  random every round. Worst-case sizing (`PieceCount × PieceMaxCells`, i.e. every piece rolls
  the maximum) guarantees the build plane is never too small for whatever a round produces, at
  the cost of looking oversized on an average or small-roll round. A smaller, average-case
  estimate looks better most rounds but risks a run of large rolls overflowing the plane —
  which fails safe today (`BuildManager` already rejects any placement whose cells land outside
  `GridUtil.isInside`), just as a placement UX dead-end rather than a crash, on whatever round
  hits it. Recommendation: worst-case, matching the "err safe" precedent `BuildZoneSize`
  already sets today (sized off the full block total, not a typical one). Needs a decision
  before Phase 1, since it's a data-shape/sizing-formula change to something the arena's static
  geometry depends on.
