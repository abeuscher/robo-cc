# Session 013 — Weapon Spin & Trajectory-Bounce — Log

**Date:** 2026-09-13
**Branch:** session-013
**Roadmap section:** Pass 13 — Weapon Spin & Trajectory/Bounce

## What was built

### Phase 1 — `Config`

- Added `CatapultMaxSpin` (10, rad/s at full spin) and `CatapultMagnusCoefficient` (0.008) —
  catapult only, per the Open Gate decision. Defined as an acceleration coefficient rather than a
  raw force, so the curve stays mass-independent, the same reason gravity already doesn't depend
  on projectile mass in this codebase. The ballista deliberately gets no spin tunables at all,
  preserving its flat-trajectory identity.

### Phase 2 — Server: `WeaponManager`

- `WeaponManager.fire()` gained a `spin` parameter. For the catapult it sets an initial
  `AssemblyAngularVelocity` about the world Y axis and attaches a per-frame Magnus-style
  `VectorForce` (new `attachMagnus()`), recomputed every Heartbeat (`updateMagnus()`) from the
  ball's *live* velocity — force = mass × acceleration, so the tuned curve doesn't depend on the
  ball's own mass. The force is removed on the ball's first `Touched`, i.e. active only while
  airborne, per the brief.
- `clearAll()` now also wipes the `magnusActive` tracking table on round reset.
- `onFireWeapon` reads `payload.spin` and passes it through; the ballista branch of `fire()`
  never applies spin regardless of what a client sends.

### Phase 3 — Client: `AttackInput`

- Replaced the two-click launch meter with a **three-stage, same-button sequence** (the user's
  own design, proposed mid-session as a golf-swing-meter pattern): click 1 locks aim and starts
  the power meter (unchanged); click 2 freezes power — the ballista fires immediately, unchanged;
  the catapult instead opens a second, smaller meter above the power one that oscillates
  left-right continuously (a looping linear triangle wave, `triangleWave()`), its frequency
  scaling with how hard the power swing was (`SPIN_OSC_MIN_FREQ` 0.5 Hz → `SPIN_OSC_MAX_FREQ` 2
  Hz); click 3 freezes spin and fires. Timeout behavior is deliberately asymmetric: letting the
  power meter run out still cancels the shot (unchanged); letting the spin meter run out instead
  still fires, pinned to full spin at the rightmost extreme (`SPIN_TIMEOUT` 3s) — the user's
  explicit choice, not a default I picked.
- New `makeSpinMeter()` builds the small horizontal track, centre tick, and sliding indicator;
  `updateSpinIndicator()` positions it each frame.
- `stepTrace`/`traceShot`/`showTrace` all take an optional spin vector and apply the identical
  per-step Magnus acceleration the server does, so the crosshair and dashed line curve live while
  the spin meter oscillates — full trace fidelity, per the Open Gate answer, not a cheaper
  straight-line approximation.
- `Types.ShotPayload` gained `spin: number`.

### Open Gate decisions

- **Which weapon(s) get spin:** catapult only — preserves the ballista's spec identity as a
  precise flat shot.
- **Randomized or aimed:** aimed/controlled — settled further mid-session into the three-click
  meter design above, replacing an initially-proposed A/D key control that was never built.
- **Client trace fidelity:** matches the server's curve exactly.

## Playtest result

Two-player Studio playtest run by the user. Reported result: "this works as expected and the
game is starting to balance a bit." No bugs reported, no follow-up scope changes requested — the
spin meter, the curving catapult arc, and the live trace preview all read correctly, and the
ballista's unchanged flat shot still reads as distinct from the catapult's new curving arc.
