**Roadmap section:** Pass 8 — Randomized Piece Generation

## What was built

### Phase 1 — `Config`

- Dropped `BlockTypes`/`L_SHAPE`/`BlockCount` entirely (confirmed via grep: `BlockCount` had no
  other readers, and `Arena.build()` no longer looped over `BlockTypes` since session 006
  removed the pile-marker code -- full replacement was safe).
- Added `PieceGridSize = 3`, `PieceMinCells = 3`, `PieceMaxCells = 6`, `PieceCount = 9`.
- `BuildZoneSize` re-derived off `PieceCount x PieceGridSize` rather than the brief's original
  `PieceCount x PieceMaxCells` -- corrected during the Open Gate: a piece's cells are always
  drawn from a fixed 3x3 area, so its bounding box can never exceed 3x3 regardless of how many
  of those cells end up filled. Cell count affects mass and shape variety, not footprint extent.
  `PieceMaxCells` would have sized the trench off the wrong worst case.

### Phase 2 — `BlockManager` — generate instead of look up

- `resetQueue()` generates `PieceCount` random shapes each round: shuffle the 9 candidate cells
  in the grid, take a random count in `[PieceMinCells, PieceMaxCells]`, normalize.
- Added a flood-fill `connectedComponents()` that splits a shape's cells into edge-adjacent
  groups (4-connectivity) once at generation time -- rotation and mirroring both preserve
  adjacency, so this never needs recomputing per placement, only per piece.
- `placeCurrent()` builds each component independently: 2+ cells become a `UnionOperation`
  (as session 005 established for the always-fully-connected L-piece); exactly 1 cell becomes a
  plain `Part` instead, since unioning a single part has no purpose. Each component gets its own
  measured `pivotDelta` and its own `BlockId`, landing in the same `placedParts` list
  `releaseAll()` already walked unconditionally -- no change needed there.
- The trickiest correctness point: mirroring has to re-partition the flattened cell list back
  into the original component groupings after transforming it, which only works because
  `GridUtil.mirrorShape`/`rotateShape` preserve each cell's position in the list (never
  reordering, only moving where it sits on the grid) -- verified this by hand rather than just
  trusting it compiled. Rotation itself is *not* applied to the shape before building geometry --
  it stays deferred to the final `CFrame`, exactly as the single-body case already worked; only
  the mirror (which can't be expressed as a rigid transform) needed to touch the build-time cell
  positions at all.

### Phase 3 — `BuildManager` / `MatchController` — plain counts, no type names

- `onPlaceBlock` reads `BlockManager.currentShape()` (a flat cell list) instead of a type def.
- `blocksRemaining` collapsed from a per-type-name table to a plain number end to end;
  `MatchController.initialRemaining()` was trivial enough at that point to just inline as
  `Config.PieceCount` and remove.
- `MatchController` now also broadcasts `currentShape` on every `StateChanged`, computed fresh
  and `nil` outside BUILD -- the same pattern session 007 established for `currentWeapon`.

### Phase 4 — `Types`

- Dropped the now-meaningless `BlockType` alias. `BlocksRemaining` became a plain `number`.
- Added `PieceShape` and `currentShape: PieceShape?` on `StatePayload`.

### Phase 5 — `BuildInput` / `Hud`

- `BuildInput` dropped the static `PIECE_SHAPE` constant; a module-level `pieceShape` now mirrors
  `StateChanged.currentShape` on *every* broadcast while active, not just on activation, since a
  fresh piece arrives after every single placement -- this also corrected the stale comment
  session 007's log had flagged ("session 007 makes this per-piece and random," left over from
  before the shot-sequence work took that slot).
- `Hud`'s blocks-remaining line reads the plain count directly instead of `.LPiece`.

### Small addition beyond the brief's file list

- `GridUtil.normalizeShape` was a private local helper shared internally by `rotateShape`/
  `mirrorShape`. The random-generation code needed that exact same normalization after picking
  cells, so it was exported (`GridUtil.normalizeShape`) rather than duplicated -- a pure
  visibility change, no behavior difference, so `GridUtil` itself stayed otherwise untouched as
  the brief anticipated.

change both weapons' projectiles from an abstract raycast hit-probe into real physical objects

`WeaponManager`'s own header comment) to deserve its own playtest in isolation.

That session's brief, `sessions/009. Physical Projectiles — Brief.md`, was drafted and then
revised twice more in the same conversation as the user resolved its own open questions:

- Both weapons throw a ball (not a ballista-specific puck) -- a puck risks tumbling
  unpredictably under real physics, a ball doesn't. Differentiated by mass and speed instead of
  shape: the ballista light and fast, the catapult heavy and slower with more bounce. Under
  Roblox's default (drag-free) gravity, mass doesn't affect trajectory curvature at all -- only
  speed keeps the ballista's arc reading as flat, which is why "light" (not "dense") is the
  correct lever for reducing its impact without slowing it down.
- The Princess's win condition changes from a touch/velocity check to a purely physical one: she
  must be knocked onto her side. This replaces (not generalizes) both of today's kill paths --
  a raycast-reported direct hit, and `Touched`-by-a-fast-`BlockId`-part -- with a single
  continuous tilt-angle check against her own `CFrame`, once she becomes a real unanchored body
  for the first time. This is itself a difficulty increase, independent of and additive with the
  force reduction: a graze that scores a kill today might not tip her over.
